# Приёмка одной кампании на Windows

Дата подготовки: 20.11.2026. Статус сценария: **NOT_RUN**.
Документ описывает будущую проверку; он не подтверждает выполнение шагов и не
разрешает включать внешние интеграции сам по себе.

Цель — проследить одну кампанию от согласованной стратегии до одной публикации
в одном выбранном канале, затем до наблюдаемых результатов и решения человека.
Граница первой приёмки: одна статья, один действующий пункт медиаплана,
один выбранный пост и одна внешняя отправка. Дополнительные статьи, каналы
и отправки в этот сценарий не входят. Текущая схема стратегии требует пакет
из 5–10 постов (SocialStrategy.post_count); границу генерации черновиков
нужно решить до этапа B, она не расширяется этим документом автоматически.

## Исходное состояние и запись допуска

Принят перенос изолированной копии Windows от 19.11.2026: 35 таблиц,
релиз `ee7e1e0b61f2e0c63ea5d0a01c2d91e0ff64cb15`, Alembic
`20261009_0028`, четыре сервиса просмотра. Это историческая приёмка переноса,
а не подтверждение текущего runtime или будущего релиза из `development`.
Изменение `replan` должно отдельно пройти три регрессионных теста с PostgreSQL
и обычные проверки CI до использования исправления в рабочей среде.

Перед выполнением заполнить:

| Поле | Значение |
| --- | --- |
| Оператор, дата и часовой пояс | `<заполнить>` |
| Среда и точный Git SHA/образы | `<заполнить>` |
| Этап A: изолированная проверка | `NOT_RUN` |
| Допуск к этапу B: AI, предел расходов/времени, разрешённые роли | `<не выдан / ссылка и границы>` |
| Граница SMM: разрешён пакет черновиков 5–10 или отдельно принят режим одного поста | `<решение не принято; до него B BLOCKED>` |
| Допуск к этапу C: выбранный канал и точный target | `<не выдан / ссылка и границы>` |
| Допуск к чтению внешних метрик | `<не выдан / ссылка и границы>` |
| Кампания, статья, пост, версия, план, Publication | `<UUID заполняются по мере выполнения>` |

Разрешения на AI, отправку и чтение метрик фиксируются отдельно. До соответствующего
допуска publishing, metrics и фоновые исполнители, способные вызвать провайдера,
остаются выключенными. Настройки принятой копии не используются как тестовые.

Проверки с изменением бизнес-данных выполняются в явно выбранной среде через
приложение. Изолированные автотесты используют отдельные PostgreSQL `*_test`
и Redis, синтетические данные и подменённые ответы AI/провайдеров; accepted
volumes и исходная БД не подключаются к destructive fixtures.

## Этап A — проверка без внешних вызовов

| Шаг | Действие | Ожидаемое наблюдение и доказательство |
| --- | --- | --- |
| A1 | Проверить точный SHA, schema, health/readiness, образы и подключения volumes тестовой/просмотровой среды. В принятой копии только читать. | Нет чужого volume, bind mount или credentials mount; выбранная среда указана в отчёте. Факт работы workers не выводится из одного флага enabled. |
| A2 | В отдельной тестовой БД выполнить `test_publication_replan_versions.py` и профильные проверки workflow, SMM, публикаций, metrics и optimization apply. | Записаны точная команда, SHA, число успешных/неуспешных тестов и безопасный лог. Это подтверждение работы с mock-ответами, не реальной отправки. |
| A3 | На синтетических данных пройти положительный путь стратегии, исследования, статьи, согласования, плана, поста и имитированного результата. | Видны связи task → run → content/version → approval → publication; успешные downstream действия возникают только после своих условий. |
| A4 | Проверить сохранение данных после обновления страниц и повторного входа. Открыть `/campaigns/{id}`, `/content/{id}`, `/publications`, `/approvals`. | Нет повторного создания кампании, задачи, версии или Publication из-за перезагрузки; ошибки загрузки не выглядят как отсутствие данных. |
| A5 | Проверить три сценария версий: SCHEDULED v1 при approved current v2; CANCELLED v1 при approved v2; SCHEDULED v1 без действующего approval. | Перенос даты сохраняет v1; повторное планирование отменённого допускает v2; отсутствие approval v1 блокирует перенос до отмены и создания replacement. История и approved plan неизменны. |
| A6 | Имитировать сбой очереди, повторный callback и неоднозначный исход доставки. | Нет второй отправки, молчаливого retry или подстановки новой версии; видны отказ/необходимость reconciliation. |

Базовое покрытие уже имеется в `backend/app/tests/test_automatic_workflow.py`,
`test_smm_integration.py`, `test_publications.py`, `test_metrics_loop.py`,
`test_performance_analysis.py`, `test_optimization_apply.py` и новом
`test_publication_replan_versions.py`. Этот список задаёт область проверки;
он не утверждает, что перечисленные тесты уже были выполнены для нового SHA.

Этап A принят, когда положительный и отрицательные пути подтверждены в отдельной
среде, а внешние AI/provider calls равны нулю. Синтетический `PUBLISHED` явно
помечается как mock и не становится доказательством внешней доставки.

## Этап B — одна кампания с контролируемым AI

Начинать после приёмки A и явного допуска к AI. Publishing и metrics пока OFF.
До запуска dispatcher проверить все READY/QUEUED/RUNNING задачи среды: разрешение
на одну кампанию не разрешает исполнить старую очередь других кампаний.

1. На `/knowledge` сверить зарегистрированный KnowledgeStore, доступные исходные
   файлы и локальные metadata. PostgreSQL dump не содержит исходные файлы и индекс
   внешнего хранилища. Проверить принадлежность и доступность уже существующего
   store; не создавать новый автоматически при ошибке доступа. Для темы кампании
   выбрать известные документы и зафиксировать их IDs/версии/контрольные суммы
   в защищённой записи, не прикладывая секреты.
2. До генерации стратегии решить ограничение SMM: текущий
   `backend/app/schemas/agent_outputs.py` требует 5–10 постов в social strategy
   и CREATE_SOCIAL_POSTS в графе. Либо отдельно разрешить генерацию этого числа
   черновиков с выбором только одного для отправки, либо сначала принять
   продуктовую доработку режима одного поста. Пока решения нет, B — BLOCKED;
   не обходить схему и не утверждать неподходящий граф. Затем на
   `/campaigns/new` создать одну кампанию с реальной целью, аудиторией, периодом,
   одной статьёй и выбранным каналом. На странице стратегии запустить генерацию
   один раз, записать Task/AgentRun IDs. `QUEUED` означает ожидание, а не
   завершённую генерацию.
3. Проверить предложение стратегии и граф задач до «Утвердить стратегию».
   Если модель выходит за согласованное число черновиков или предлагает лишние
   статьи/каналы/действия, вернуть на доработку;
   не расширять приёмку молча. Утверждать точную версию. После согласования
   наблюдать существующий автономный dispatcher, не нажимать устаревший ручной
   `/tasks/{id}/run` для специализированной цепочки.
4. Дождаться исследования и статьи, проверить источники и отсутствие выдуманных
   ссылок. Открыть статью `/content/{id}`, проверить точный текст и утвердить
   конкретную версию. При недостатке знаний или failed run записать причину;
   не отмечать этот шаг успешным по одному наличию ContentItem.
5. Подготовить медиаплан, связанный с утверждённой версией статьи: один пункт,
   один канал, будущая timezone-aware дата. Проверить и отдельно утвердить план.
   **Текущая кнопка «Создать медиаплан» запрашивает два канала и шесть пунктов.**
   Для узкой приёмки использовать аутентифицированный application API
   `POST /api/v1/campaigns/{id}/publication-plans/generate` с
   `channels: ["<выбранный канал>"]`, `total_items: 1` и будущим горизонтом;
   либо убрать лишние пункты ещё в DRAFT до согласования. Если результат уже
   WAITING_APPROVAL, вернуть его в DRAFT штатным переходом до редактирования.
   Утверждённый план не редактировать напрямую.
6. Для единственного пункта использовать «Создать пост», если пост ещё не создан.
   Если стратегия уже породила подходящий материал, сначала проверить его связь
   с точным пунктом/статьёй; не создавать дубль. Дождаться завершения задачи,
   проверить текст и точную версию источника, выполнить предусмотренное
   согласование пакета/поста. Не принимать старый материал другого плана.
7. Через «Запланировать публикацию» подготовить одну Publication. До перехода
   к отправке сверить ContentVersion UUID, канал и эффективное время с human
   approval и approved планом/аудитом переноса, а ожидаемый target — с выбранной
   конфигурацией. Durable `provider_target_id` закрепляется при claim перед
   отправкой, поэтому его пустое значение до claim само по себе не ошибка.
   Наличие SCHEDULED при выключенном provider не означает готовую внешнюю доставку.

После обновления страниц стратегия, статья, план, пост, approvals и их ссылки
должны совпасть с записанными IDs. Внешних отправок на этапе B — ноль.

## Этап C — одна разрешённая внешняя отправка и результаты

До включения выбранного канала повторить inventory всей среды, проверить
завершение старых/неоднозначных попыток и отсутствие второго отправляющего
экземпляра. В принятой копии известна одна просроченная VK SCHEDULED: человек
должен отдельно решить через приложение, отменить её или перенести. Не включать
dispatcher при неразобранных due rows, чтобы допуск одной новой публикации
не отправил старые. Historical FAILED Telegram не повторять автоматически.

Историческая canary `1142723f-4c25-4334-8f22-7e3ceb1f55f4` уже PUBLISHED,
использованные grants/approvals не сбрасываются. Эта приёмка не повторяет её
и не создаёт новую canary; для live-пути выбирается содержательная публикация
из согласованной кампании. Проверка и rotation credentials — отдельная
разрешённая операция, выполняемая без вывода токенов.

| Шаг | Действие | Критерий |
| --- | --- | --- |
| C1 | После допуска проверить credentials, exact target, готовность соответствующих исполнителей и расписания. Второй канал оставить выключенным. | Записано свежее подтверждение; enabled-флаг сам по себе недостаточен. |
| C2 | Разрешить выбранную согласованную Publication и дождаться штатного dispatch по времени. | Один durable intent и одна доставка; состояние PUBLISHED с `external_id`, `published_at`, точным `provider_target_id` и опубликованной согласованной версией. |
| C3 | Человек открывает внешний пост и сверяет текст/адресата с согласованной версией. Обновляет приложение. | Внешний факт подтверждён ссылкой; обновление не отправляет повторно. При timeout/ambiguity — остановка и reconciliation, без повторного клика отправки. |
| C4 | После отдельного допуска read-only metrics получить существующие наблюдения этой публикации либо ввести явно ручные показатели через приложение. | Источник, время наблюдения и target сохранены; недоступные счётчики остаются NULL, не выдуманным нулём. |
| C5 | На `/campaigns/{id}/performance` проверить результат, KPI и feedback; запустить один анализ в пределах AI-допуска, затем принять или отклонить его. | Анализ ссылается только на доступные frozen evidence; отсутствие/недостаток данных явно показаны. |
| C6 | Если данные обосновывают действие, рассмотреть существующее предложение оптимизации и отдельно решить approve/reject/apply. | Проверены тип действия, target/version и provenance; утверждение рекомендации само по себе не меняет текст/расписание и не отправляет пост. Apply создаёт предусмотренный артефакт с отдельными дальнейшими согласованиями. |

Для C6 допустимо решение NO_CHANGE/отказ от действия при недостаточных данных.
Искусственная рекомендация ради отметки PASS не требуется. Новые версии контента
и планы остаются отдельными артефактами; уже опубликованная версия сохраняется.

## Условия остановки и итоговая запись

Остановиться на первом несоответствии среды/SHA/schema/volumes, потере источников,
расхождении версии/канала/target, дублирующей задаче/Publication, необъяснённой
отправке, устаревшем согласовании или неоднозначном provider outcome. Записать
безопасный код ошибки и IDs; не исправлять business-state SQL, не удалять volumes,
не переимпортировать БД и не сбрасывать consumed grants ради повторной проверки.

Запись выполнения не содержит `.env`, паролей, токенов, полных prompts/provider
bodies или лишних персональных данных. Для каждого шага фиксировать:

| Поле результата | Заполняется оператором |
| --- | --- |
| Run ID, среда, точный SHA/образы, Alembic | `<заполнить>` |
| Шаг, время UTC и локальный часовой пояс | `<заполнить>` |
| Итог | `NOT_RUN / PASS / FAIL / BLOCKED` |
| IDs и точные версии участвующих артефактов | `<заполнить>` |
| Команда/действие, безопасный лог или screenshot | `<защищённое расположение без секретов>` |
| Фактические AI calls / provider reads / provider writes | `<измеренные значения либо NOT_MEASURED>` |
| Дефект, решение и следующий разрешённый шаг | `<заполнить>` |

Общий PASS сквозной рабочей кампании присваивается только после A, B и C1–C5.
Применение оптимизации C6 имеет собственный итог; отсутствие обоснованного
изменения не маскируется фиктивным применением. До завершения C внешний цикл
помечается NOT_RUN/BLOCKED, даже если все mock-тесты прошли.
