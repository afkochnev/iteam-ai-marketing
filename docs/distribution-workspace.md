# Рабочее место публикаций: серверная модель чтения

## Назначение

`/publications` получает подготовленные карточки из одного
`GET /api/v1/distribution-workspace`. Сервер определяет готовность материала,
разделы публикации, доступные действия и наличие замены отменённой записи.
Браузер отображает результат, форматирует время и собирает ввод для существующих
команд. Начальная загрузка больше не объединяет списки кампаний, материалов,
медиапланов и публикаций на клиенте.

Это ограниченный шаг стабилизации article → social workflow. Он не вводит
DeliveryAttempt, transactional outbox, универсальную модель контента или новую
модель авторизации Workspace. Общая архитектура моделей чтения описана в
[ADR 006](adr/006-server-side-read-models.md); статус самого ADR этим изменением
не меняется.

## Контракт

| Параметр | Значение |
| --- | --- |
| `campaign_id` | Необязательный UUID кампании. Без него доступна общая область текущего приложения. |
| `limit` | Размер страницы: по умолчанию 50, допустимо от 1 до 100. |
| `cursor` | Непрозрачный указатель следующей страницы из предыдущего ответа. Привязан к фильтру кампании. |

Ответ содержит:

- `as_of`: серверное время снимка, используемое в том числе при определении
  просрочки;
- `campaign`: идентификатор, название и статус выбранной кампании либо `null`
  для общего списка;
- `items`: ограниченный список карточек с `kind: publication | candidate`;
- `pagination`: применённый `limit`, `has_more` и `next_cursor`;
- `counts`: счётчики разделов **на этой странице**, а не во всей базе.

Порядок страниц детерминирован. Данные, влияющие на готовность, наличие замены и
выбор основной отменённой карточки, проверяются по всей соответствующей области,
даже когда связанная публикация не попала на текущую страницу.

Успешный ответ полностью описывает возвращённую страницу. Это не обещание полной
выгрузки всех публикаций: старые записи доступны через навигацию по страницам.
Сообщения об отсутствии карточек и счётчики интерфейса относятся к текущей
странице. Разделы могут пересекаться: например, публикация с ошибкой может также
отображаться в своём основном разделе, а основная отменённая карточка остаётся
частью истории отмен.

## Точная версия, история и действия

Карточка публикации всегда сохраняет `Publication.content_version_id`.
Изменение текущей версии материала не меняет отображаемую версию ранее
запланированной или отправленной публикации. Название материала служит ссылкой
для навигации; оно не является копией опубликованного текста. Кандидат на
планирование содержит точную согласованную текущую версию и её номер.

Сервер задаёт:

- `sections` публикации: `active`, `upcoming`, `overdue`, `attention`,
  `published`, `cancelled`, `cancelled_history`;
- `state` кандидата: `ready`, `needs_plan`, `overdue`;
- `allowed_actions`: доступные на момент снимка команды;
- `has_replacement`: есть ли действующая запланированная, отправляемая или
  опубликованная замена, включая публикацию копии материала;
- `content_source_archived`: относится ли публикация к архивному материалу
  или кампании.

История отмен не удаляется при появлении новой публикации. Операционная карточка
отмены выбирается на сервере по материалу и каналу; исторические записи остаются
доступны отдельно. Опубликованный факт не становится кандидатом на новую отправку
из-за наличия старой отмены. Общий список также сохраняет историю архивных
кампаний; для архивных кампаний новые кандидаты на планирование не создаются.

`provider_enabled` означает настройку разрешения отправки соответствующему
провайдеру. Этот флаг не подтверждает доступность воркера, действительность
учётных данных или факт доставки. Неопределённый результат отправки требует
существующего процесса сверки, а не автоматического повторения.

Плановый слот кандидата просрочен после наступления его времени. Для уже
существующей `SCHEDULED` публикации сохраняется установленный в приложении допуск
`publication_auto_dispatch_max_lateness_seconds`. Оба расчёта используют один
серверный `as_of`, а не часы браузера.

## Согласованность и ошибки обновления

Каждый GET читает отдельную транзакцию PostgreSQL `REPEATABLE READ, READ ONLY`.
Режим устанавливается до первого запроса данных. Уже открытая при обычной
аутентификации транзакция не переиспользуется для смены уровня изоляции.
Активность пользователя и версия его авторизации повторно проверяются внутри
снимка. Сессия чтения закрывается после ответа.

Это согласованность **одного HTTP-ответа**. Между переходами по страницам данные
могут измениться. Интерфейс заменяет страницу целиком и показывает новое
`as_of`; он не объединяет разные страницы в якобы единый замороженный снимок.
После успешной команды выполняется новый GET вместо локальной подмены одной
публикации в старых списках.

При ошибке повторного чтения прежний успешный снимок сохраняется целиком,
обозначается как устаревший, а действия временно недоступны. Ошибка первого
чтения не представляется пустой базой. Запоздавший ответ старого запроса не может
заменить данные нового фильтра кампании. Смена фильтра не переносит старый
снимок в другую кампанию.

## Доступ и границы чтения

Endpoint использует действующую авторизацию приложения: активные `ADMIN` и
`MANAGER` имеют общую область кампаний. `created_by` не является границей доступа.
Этот endpoint не заявляет изоляцию нескольких tenants: существующие бизнес-таблицы
ещё не привязаны к Workspace.

GET не изменяет бизнес-данные, не записывает аудит, не запускает Celery, не
обращается к Redis, AI или внешним провайдерам. Связанные данные выбираются
пакетами для ограниченной страницы; полные версии материалов и списки всех
кампаний не загружаются в память для последующего объединения.

`allowed_actions` описывает состояние снимка и не заменяет разрешение команды.
Существующие endpoints согласования, планирования, переноса, отмены, отправки,
повтора и сверки повторно проверяют актуальное состояние. Изменения после GET
могут привести к отказу команды; интерфейс показывает этот отказ. Отдельные
запросы предпросмотра массового переноса и смены канала остаются явными
действиями оператора.

## Проверки

Регрессионные проверки страницы находятся в
`frontend/tests/publications.test.tsx`; интеграционные проверки модели чтения —
в `backend/app/tests/test_distribution_workspace.py`. Основные риски: точная
версия, согласования пакета постов, история отмен и замена вне страницы, границы
кампании и курсора, права, согласованность транзакции и ограниченное число SQL
запросов. Проверки frontend подтверждают серверное управление разделами и
действиями, повторное чтение после команды и обработку устаревших ответов.

Полный CI дополнительно запускает существующие backend/frontend регрессии,
проверки миграций и release tooling. Схема базы и production deployment этим
изменением не затрагиваются.
