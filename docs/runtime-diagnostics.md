# Диагностика исполнителей и очередей

Статус приёмки нового runtime: **NOT_RUN**. Документ описывает доработку в
`development`; он не подтверждает её развёртывание или запуск исполнителей.

На главной странице администратору доступна панель «Исполнители и очереди».
Кнопка «Проверить исполнителей и очереди» выполняет только
`GET /api/v1/system/runtime`. Автоматического опроса нет. Менеджеру и
неавторизованному пользователю API отвечает 403 и 401 соответственно.
Существующий `/system/status` сохраняет бизнес-счётчики и прежний контракт.

## Что означает снимок

`sampled_at` — время наблюдения. Успешное чтение использует часы самого Redis,
поэтому свежесть heartbeat не зависит от часов процесса, который его отправил.
Панель показывает результат на этот момент; это не постоянная проверка сервиса.

| Поле | Значение |
| --- | --- |
| `broker_state=ok` | Диагностические данные удалось прочитать. |
| `partial` | Отдельная очередь или наблюдение недоступны/некорректны; остальные результаты сохранены. |
| `unavailable` | Чтение брокера завершилось ошибкой или таймаутом. Неизвестное значение не подменяется нулём. |
| `unsupported` | Транспорт или его схема очередей не поддерживаются. В тестовом режиме с `memory://` Redis-очереди не считываются. |
| `disabled` | Выключен именно сбор диагностики, а не исполнители или публикация. |
| `queues[].waiting_messages` | Число сообщений, ещё ожидающих в Redis; `null` означает неизвестное значение. |
| `processes[].last_seen_at` | Последнее допустимое наблюдение процесса в сохранённом окне. |
| `observed_instances` / `fresh_instances` | Количество наблюдавшихся экземпляров и экземпляров со свежим сигналом. |
| `processes[].queues` | Реальные очереди, наблюдавшиеся у свежих экземпляров worker. |
| `build_mismatch` | Среди свежих сигналов есть известный SHA сборки, отличный от SHA backend; `null` — сравнение не подтверждено. |

Состояние сигнала `recent` означает наблюдение не старше 60 секунд; `stale` —
сохранённый, но устаревший сигнал; `unobserved` — сигнала нет в доступном окне;
`unknown` — данные невозможно надёжно прочитать или разобрать. Эти состояния
не означают «включён», «выключен» или «готов к отправке».

Пустая очередь не подтверждает наличие исполнителя. Отсутствие сигнала не
доказывает остановку процесса: он мог ещё не работать с этой версией телеметрии.
Heartbeat не проверяет credentials, внешний канал, завершение AI-запроса,
успешность публикации или своевременность всех заданий расписания.

После истечения `stale_after_seconds` панель помечает снимок устаревшим и
скрывает текущие числовые значения. Ошибка обновления убирает прежний снимок,
чтобы старые сведения не выглядели свежими. Для нового наблюдения нужна кнопка
проверки. Панель не запускает задачи, повторные попытки и отправки.

## Какие процессы наблюдаются

| Тип | Роли |
| --- | --- |
| Worker | `ai`, `ai_control`, `publication`, `publication_control`, `metrics` |
| Scheduler | `ai`, `publication` |

Allowlist очередей: `ai`, `ai_control`, `ai_live_test`, `publication`,
`publication_control`, `metrics`, `unrouted`. Роль `ai` сама по себе не
подтверждает потребление обычной очереди `ai`: изолированный worker может
читать только `ai_live_test`. Поэтому сигнал содержит реальные очереди
consumer, а не предполагаемую связь роли с очередью. Scheduler не объявляется
потребителем очереди.

Принятая конфигурация изолированной Windows-копии предусматривает только четыре сервиса просмотра.
Без новых workers/schedulers отсутствие их наблюдений ожидаемо. Состав
ожидаемых процессов не выводится из provider flags или `worker_role=None`.
Новый API не разрешает включение AI, providers, metrics или внешней сети.

## Сбор и хранение

`RUNTIME_DIAGNOSTICS_ENABLED` по умолчанию включён. Значение `false` отключает
чтение снимка и публикацию heartbeat. Для остальных процессов это изменение
конфигурации применяется при их следующем разрешённом запуске.

HTTP-запрос выполняет пассивные `TIME`, `LLEN` и ограниченные `ZREVRANGE`.
Он не вызывает Celery inspect, не читает тела сообщений и не извлекает задания
из очередей. Длина очереди суммирует списки приоритетов Kombu с учётом
`priority_steps`, `sep` и `global_keyprefix`. Она не включает уже полученные
worker задания и не является возрастом самого старого сообщения. Чтение
ограничено по времени; ошибка Redis возвращает безопасное неизвестное состояние.

Worker публикует сигнал после готовности consumer, затем с ограничением частоты
раз в 15 секунд. Сигналы остановки запрещают последующие обновления. Scheduler
публикует наблюдение после завершившейся итерации `PersistentScheduler.tick()`;
это подтверждает итерацию цикла, а не доставку конкретного задания.

Телеметрия хранится в текущей Redis logical DB, в namespace
`<global_keyprefix>iteam:runtime:v1:<kind>:<role>`. Для каждой роли сохраняются
не более 100 наблюдений в окне до 600 секунд. Экземпляр имеет случайный ID;
при завершении удаляются только его собственные записи. Истечение окна не
создаёт бизнес-событие и не удаляет историю задач или публикаций в PostgreSQL.

В наблюдении разрешены только ID экземпляра, нормализованный SHA сборки и
очереди из allowlist. Hostname, environment, URL подключения, credentials,
тексты задач и сообщений в ответ не включаются. Ошибка телеметрии не должна
останавливать бизнес-обработку. При импорте API/Celery app соединение для
публикации heartbeat не открывается. Миграции БД для этой доработки не нужны.

## Проверка до приёмки

Подготовленные проверки находятся в:

- `backend/app/tests/test_runtime_diagnostics.py` — границы чтения, приоритеты,
  namespace, свежесть, malformed/timeout/WRONGTYPE, memory transport и API RBAC;
- `backend/app/tests/test_runtime_heartbeat.py` — lifecycle, throttling,
  shutdown, реальные имена очередей и best-effort запись;
- `frontend/tests/runtime-diagnostics.test.tsx` — ручной запрос, права,
  unknown, ошибки обновления, истечение снимка и поздние ответы.

Интеграционные проверки выполняются только в отдельной PostgreSQL `*_test`
и Redis с ненулевой logical DB; для данных теста используется отдельный prefix.
Нужна проверка, что чтение не уменьшило длину синтетической очереди и не изменило
тела сообщений. Рабочие volumes и credentials к стенду не подключаются.

Для фактической приёмки после отдельного разрешённого развёртывания зафиксировать
точный SHA и среду, проверить свежий сигнал, его устаревание/исчезновение после
остановки, два экземпляра одной роли, отказ Redis и восстановление. Отдельно
подтвердить, что UI не обещает готовность отправки по одному heartbeat.
До записи этих результатов статус фактической приёмки остаётся `NOT_RUN`.
