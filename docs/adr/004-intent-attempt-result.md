# ADR 004: intent, attempt и result

- Status: **Proposed**.
- Date: 2026-11-21.
- Scope: PR-A0, documentation-only.

## Context

Одно поле статуса не может одновременно описывать план, сетевую попытку, факт внешнего размещения и наблюдение бизнес-результата. Отмена старой записи не отменяет уже опубликованный пост. Потеря ответа provider не доказывает отсутствие отправки, а наличие worker не доказывает доставку.

## Decision

Использовать три отдельных понятия: **DistributionIntent** — разрешённое намерение с immutable revisions; **DeliveryAttempt** — конкретный сетевой запуск; **ExternalPlacement** — подтверждённая внешняя идентичность/результат с историей версий. Дополнительно Observation фиксирует факт измерения, Decision — предложение или принятое человеком решение на основании evidence.

Согласование content отделено от execution approval. Attempt связывает exact version/target и execution ownership token. UNKNOWN блокирует blind retry до supported reconciliation; cancel intent останавливает будущие claims, но не стирает известные факты и не отзывает уже отправленный запрос.

Успех соответствует конкретному action kind: CMS draft не равен публичной статье; email acceptance не равен доставке адресату. Позднее валидное подтверждение доставки сохраняется и сверяется, даже если intent уже изменён/отменён. Автоматической гарантии exactly-once внешнего эффекта нет.

## Alternatives

- Единый Publication status для плана/попыток/результата: неоднозначная история и опасные повторные действия.
- Только provider logs как факт: недостаточная связность с approval, версией и Campaign.
- Считать любой timeout неотправленным: создаёт дубли при фактическом success без ответа.

## Consequences

UI должен показывать отдельно расписание, попытки и подтверждённые placements. Нужны evidence-based reconciliation и понятные действия оператора. Разные каналы имеют общий контракт, но сохраняют разные уровни подтверждения и cardinality.

Текущий Publication не заменяется этим PR. Миграция и mapping historical evidence выполняются отдельно без выдумывания отсутствующих фактов. Открытые вопросы: Q3, Q4, Q6, Q10 в [roadmap](../architecture-v2/roadmap.md).

## Учёт попыток действующего механизма публикаций

С ревизии `20261123_0032` обработчик Telegram или VK связывает начало исполнения с ранее записанным разрешением. Ключ `legacy_publication_attempts.claim_event_id` указывает на `publication_claim_events.id`. Через эту связь доступны публикация, согласованная версия контента и канал. У одного разрешения может быть одна логическая попытка. Если обработка ещё не началась, строки попытки нет. Для разрешений, созданных до внедрения событий, история задним числом не формируется.

| Состояние | Что зафиксировано |
| --- | --- |
| `STARTED` | Работник зафиксировал начало попытки перед вызовом провайдера. Факт получения запроса провайдером пока неизвестен. |
| `SUCCEEDED` | Провайдер вернул внешний ID. Для Telegram сохраняется ID чата из ответа, для VK — ID владельца стены из подтверждённого запроса. |
| `FAILED` | Получен определённый отказ либо установлено, что запрос не мог быть отправлен. |
| `UNKNOWN` | Результат нельзя установить по имеющимся данным. Для продолжения нужна сверка. |

Позднее подтверждение после восстановления хранится в журнале как `PUBLICATION_LATE_PROVIDER_RECEIPT` и связано с исходным разрешением по публикации и отпечатку токена. Оно даёт оператору внешний ID для сверки. Хранилище попыток дополняет существующую публикацию. Полная модель версий `DistributionIntent` остаётся отдельной частью архитектуры.

## Подтверждённые размещения Telegram и VK

Ревизия `20261123_0033` добавляет реестр `legacy_external_placements`. Успешная попытка, для которой проверены площадка и внешний ID объекта, получает запись в реестре в транзакции обработки квитанции. Через `claim_event_id` видны конкретная попытка и согласованная версия материала. Для Telegram внешняя идентичность включает чат и номер сообщения, для VK — владельца стены и номер поста. Номер объекта может повторяться на другой площадке.

Поздняя квитанция и ручная сверка сохраняют собственную историю. Если квитанция другой публикации указывает на уже занятый внешний объект, исходная привязка сохраняется, а конфликт требует сверки. Миграция оставляет старые публикации и метрики с их исходными доказательствами. Подтверждённое размещение защищает историю соответствующей попытки от удаления.

При чтении метрик проверяются площадка и объект. Ответ `GET /api/v1/publications/{publication_id}/metrics` показывает ID размещения даже до первого наблюдения. Снимок, полученный от провайдера для этого объекта, сохраняет тот же `external_placement_id`. Нулевой счётчик является наблюдением. Ответ без счётчиков оставляет историю снимков прежней.
